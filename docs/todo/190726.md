# Main diffs between my version/branch and the main version.

## Motivations for redesigns

* Implementing drastic schema changes proved exceptionally difficult. Schemas were hardcoded into scripts and not centralised, therefore a simple addition of property/node/relationship would interface many deps. This also resulted in extremely long and complex code, which consequently make it difficult to work with coding agents.

* After spending time reading Neo4J's import documentation, I did not see the need for a PostgreSQL intermediary DB. CSV can work file with the bulk import tools and Python drivers available.

## Specific features

* (Optional) GDC extraction pipeline, to GDC data. GDC is the largest repo for publicly available data.

* A centralised schema, based on YAML files, define the schema at every stage, allowing end-to-end schema change by simply editing these files rather than pipeline logic in the scripts.

* Standardisation now produces the nodes / edges CSV, which are used as direct input into Neo4J.

* Live schema visualisation. Plots a dummy KG based on the defined schema, rather than static mermaid plots which are embedded into markdown.

* (MOST IMP). Standardisation has high complexity. But by implementing a 'mapping profile' system, we can use multiple definitions of datasets. The mapping profile is very useful as it communicates to the standardiser, where in the data certain nodes/edges/properties exist.

## Trade-offs

* Somewhat primitive stage means there could be bugs not yet spotted.

* Onboarding system from Ragad not yet incorporated. This can potentially be fitted to help construct mapping profiles.
